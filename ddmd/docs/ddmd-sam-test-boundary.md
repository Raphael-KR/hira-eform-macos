# DDMD SAM 시험 경로 확인 — 2026-09-09

목표는 본청구를 실행하지 않고 공식 시험 절차와 설치 코드의 업무 구분을 확인하는 것이다. 공개 공식 자료, 기존 코드 사본의 정적 분석, Windows 설치 JAR의 읽기 전용 해시 대조만 수행했다. 추가 인증·SAM 송신·통보 조회/수신·설정 변경은 하지 않았다.

## 결론

사전점검과 청구소프트웨어 검사 경로는 존재한다. 그러나 현재 한의원 인증서와 기관 설정으로 가상 SAM을 자유롭게 시험할 수 있는 공개 sandbox의 현행 이용 조건은 확인하지 못했다. `개발서버`라는 코드 표시만으로 독립된 시험 서버나 본청구 차단을 보장할 수 없다.

## 현재 설치 코드의 구분

`ClientConstants.DMD_TP_CD_STATUS_STRINGS`에 다음 매핑이 있다.

| dmdTpCd | 코드에 표시된 업무명 |
|---|---|
| 0 | 실청구 |
| 1 | 사전점검서비스 |
| 2 | 청구S/W검사 |
| 3 | 개발서버 |

`SendWebController.send`의 입력 검사는 0/1만 허용한다. `SendController.makeReqMessage`는 문서의 구분을 `DmdDoc` 본문에 옮기며 action은 `CLT_DMD_REQ`다.

특히 토큰의 `eamUgrpCode`가 업체 분기 `UGRP000004`일 때 입력 구분 0을 요구하고, 전송 본문의 `DmdDoc.dmdTpCd`를 2로 바꾼다. 따라서 화면에서 말하는 송신 기능만으로 실청구 여부를 판단해서도 안 되며, **서버가 발급한 사용자 권한과 실제 전송 DTO를 함께 확인해야 한다.** 현재 인증 토큰을 다시 읽거나 업체로 위장하지 않았다.

구분 3에는 본원 암호화 인증서와 수신처 값 00을 사용하는 분기가 있다. 그러나 확인한 MXS resource는 공통 `ebms.endpoint` 설정을 읽고 기본값 `http://ddmd.hira.or.kr/imxs/msh`를 사용한다. 해당 코드만으로 별도 개발 호스트 전환·실청구 불가·외부 개발자 접근 허용을 증명하지 못한다. 이 주소로 요청하지 않았다.

통보 문서명 배열에는 ‘사전점검서비스 결과 통보서’도 존재한다. 서버가 현재 어떤 시험 통보를 발급하는지, SAM 수신까지 제공하는지는 미검증이다.

증거: [선별한 정적 코드](../gateway_poc/evidence/sam-routing-code.txt), [Windows 설치본 해시 대조](../gateway_poc/evidence/sam-routing-library-check.json). 클라이언트·에이전트 JAR 두 개의 사본이 현재 설치본과 일치했다.

## 남은 확인과 실행 경계

외부 시험 전송을 하려면 심평원의 청구SW 검사·인증 담당 경로에서 다음을 확인해야 한다.

- 기존 DDMD를 이용하는 독립 headless 송수신 gateway의 개발·검사 신청 분류와 필요한 등록 절차.
- 업체기호 또는 자체개발 요양기관용 시험 권한 발급 여부, 연결할 인증서 종류, 현재 한의원 인증서 사용 가능 여부.
- 검사용 SAM 자료·허용 환자 식별정보·기관기호 규칙과 본청구로 접수되지 않는 공식 전송 방법.
- 개발서버 구분 3의 사용 대상, 현재 endpoint 및 접근 조건.
- 시험 접수증·심사결과·사전점검 결과 등 제공 가능한 통보 종류와 수신 시험 절차.

이는 아직 문의하지 않은 확인 항목이다. 외부 문의나 회원가입·업체 등록을 대신 실행하지 않았다. 답변 전에는 로컬 합성 SAM 파싱·압축·서명·암복호화 시험까지만 분리할 수 있고, 현재 기관 계정으로 운영 전송을 시험하지 않는다.
