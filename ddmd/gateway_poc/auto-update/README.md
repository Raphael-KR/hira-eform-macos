# 격리 macOS DDMD 자동 업데이트 실행기

현재 상태: 2026-09-09 시험용 외부 JVM과 임시 실행 환경을 제거했다.
[DDMD README](../../README.md)의 준비 조건을 충족한 뒤에만 실행한다.
이 문서는 코드의 실행 계약이며, 현재 준비 완료 또는 실행 지시가 아니다.

실행에는 이 디렉터리의 `run.command` 또는 저장소 루트의
`npm run ddmd:update`를 사용한다. 로컬 기관번호와 macOS Keychain 인증서 로더가
필요하며 비밀번호나 개인키는 argv·보고서에 저장하지 않는다. 실행 중 Windows 연결은 없다.
실서버 인증·다운로드·결과 보고와 macOS 앱 시작을 포함하므로 읽기 전용 명령이 아니다.

1. 독점 잠금을 얻고 활성 버전의 파일 해시를 계산한다.
2. 인증 후 CLT_MOD_UPT_REQ로 조회한다. 최신이면 적용/재시작/결과 보고 없이 종료한다.
3. CLT_MOD_UPT 파일을 수신해 해시와 경로를 검증한다.
4. 관리 중인 이전 JVM이 실행 중이면 PID와 실행 경로를 확인해 종료한다.
5. 별도 후보에 원본 UpdController로 적용하고 버전·해시·SQLite 무결성을 확인한다.
6. 결과 보고 파일을 원본 JVM의 자동 삭제 경로 밖으로 옮겨 보존한다.
7. 고유 앱 ID로 macOS 앱을 빌드·실행하고 Application started를 확인한다.
8. active.json을 원자적으로 전환한다. 이전 폴더는 보존한다.
9. CLT_MOD_UPT_RES의 응답을 기다린다. null 또는 true 정상 반환만 수용한다.
10. 보고 파일을 acknowledged.dat로 보존하고 다시 조회해 추가 업데이트 0개를 확인한다.

원본 보고 함수가 updated.dat를 전송 전에 삭제하는 것과 달리, 이 실행기는 응답이
불명확하면 pending.dat를 남기고 자동 재전송하지 않는다. 이 경우 다음 실행도 중단한다.
후보 검증 전 실패는 활성 포인터를 유지하고 중지한 이전 앱을 다시 연다.
활성 전환 뒤 보고 실패는 새 버전을 유지하며 pending 상태를 남긴다.
원본 백업/적용 함수는 내부 백업을 지울 수 있지만 기존 버전 폴더는 별도로 유지된다.

## 검증 범위

[실제 실행·재실행 기록](../../docs/HISTORY.md#ddmd-auto-update)과

## 사용 한계

- 현재 실행기는 호출할 때 전체 과정을 자동 수행한다. 원본 GUI의 업데이트 버튼은
  연결하지 않았고 OS 부팅 서비스·주기 작업도 등록하지 않았다.
- 코드와 실행 진입점은 저장소의 `ddmd/`에 있고, 로컬 실행 상태는 Git 제외 경로 `.local/ddmd/`에 있다.
- 외부 JVM만 별도 설치 경로를 사용한다. JVM 경로는 `.local/ddmd/config.json`에서 지정한다.
- 초기 설정은 후보의 기존 설정을 보존하면서 로컬 경로만 바꾸며 JDBC 어댑터는 소스에서 빌드한다.
  이전 임시 GUI 폴더에 의존하지 않는다. 운영 기관·SAM 데이터의 실사용 전환은 별도 검증 대상이다.
- GUI는 네트워크·하위 프로세스 실행 차단을 유지한다. 업데이트 통신만 별도 Java 경로로 한다.
- 업데이트 삭제 명령(버전 0 이하), 예상 밖 응답, 해시 불일치, 잘못된 경로는 적용하지 않는다.
- 인증서/Keychain이 잠겨 있으면 이를 우회하지 않는다. 네트워크 오류의 무제한 재시도도 없다.
- JIDE 및 서식 인자 호환 처리는 기존 Java 8 전용 실행기/agent를 재사용한다.
- SHA-256은 선행 0을 생략하는 DDMD 원본 표기와 숫자 값으로 비교한다.
  체크섬 검증이 별도의 코드 서명 신뢰 체인 검증을 대체하는 것은 아니다.

테스트: `npm run test:ddmd`

실제 결과 원본은 로컬 전용이며 저장소에 포함하지 않는다.
